# “同行”——多人共识旅行规划 Agent 项目案例

## 一句话定位

面向 3～6 位朋友结伴游的 AI 共识规划助手：成员分别表达预算、体力、作息和兴趣，系统识别冲突、生成可比较方案，并通过投票帮助团队形成可解释、可执行的旅行共识。

## 1. 问题背景

传统旅行规划工具主要回答“去哪里、怎么走”，但朋友结伴游的困难往往发生在规划之前：

- 有人希望高密度打卡，有人只想轻松休息；
- 预算、步行能力和作息差异难以公开协调；
- 多数投票可能让少数成员持续妥协；
- 大模型生成的攻略看似完整，却可能缺少真实地点、路线和约束校验。

本项目不把“生成一份攻略”作为最终目标，而把“帮助多人形成共识”作为核心价值。

## 2. 目标用户与核心场景

**目标用户**：3～6 位朋友组成的自由行团队。

**核心场景**：组织者发起旅行，邀请成员独立填写偏好；未参与成员可由组织者代填。系统汇总后识别冲突，生成三个候选方案，成员可选择 1～2 个可接受方案并投票。

## 3. 产品原则

### 混合参与

- 成员可通过邀请独立填写；
- 组织者也可代填；
- 未及时参与者可以跳过，但系统明确提示信息完整度。

### 混合录入

关键约束通过结构化表单收集，补充需求使用自然语言；出现歧义或冲突时由 AI 追问。

### 硬约束与软偏好分离

硬约束包括预算、时间、步行、必去/禁去和饮食限制，任何成员均可一票否决。软偏好采用“很想要、可以有、不感兴趣”三级表达。

### 混合公平机制

1. 硬约束一票否决；
2. 对可行方案进行认可投票，每人可选 1～2 个；
3. 平票时优先选择最低成员满意度更高的方案；
4. 再比较硬约束满足率和平均满意度；
5. 仍相同则由组织者决定。

### 共同活动与支线

默认希望全员同行；若成员必去需求与其他人的硬约束冲突，可转换为个人或分组支线，但必须先由相关成员确认。

## 4. 核心产品流程

1. 组织者创建旅行并填写共同边界；
2. 邀请成员填写个人约束与偏好，或由组织者代填；
3. AI 将自然语言需求转成结构化约束并请求确认；
4. 系统识别冲突；若无解，提供 2～3 个放宽方向供相关成员确认；
5. 地图工具检索真实 POI 与相邻路线；
6. 生成三个候选方案：一个综合均衡版、两个围绕主要冲突动态生成的方案；
7. 确定性校验器检查全部硬约束和证据；
8. 页面平铺展示预算、步行、通勤、兴趣覆盖和成员满意度；
9. 成员选择 1～2 个方案投票；
10. 根据票数和公平规则形成最终方案，并支持局部重规划。

## 5. AI 与规则系统的分工

### AI 负责

- 理解补充描述；
- 发现潜在冲突；
- 选择搜索与路线工具；
- 生成候选方案；
- 解释成员收益、妥协和方案差异；
- 在校验失败后提出修订方案。

### 确定性系统负责

- 预算、时间和步行上限；
- 必去、禁去和分组确认；
- 饮食过敏与明确禁忌；
- 行程时间重叠与返程截止；
- 地点、路线及引用真实性；
- 候选方案数量和投票规则；
- 评测指标与版本回归。

产品设计原则是：**模型负责提出，规则负责证明。**

## 6. Agent 架构

产品采用可复用的分阶段 Agent，而不是针对北京案例写死的生成 Demo：

- 接受任意目的地、出发点及 2～8 位成员；
- 根据成员数量、必去诉求和最严格约束动态构造协商方向；
- 使用目标城市动态调用腾讯地图地点搜索与路线规划；
- 采用“观察约束 → 有界检索 → 生成候选 → 路线补证 → 确定性校验 → 一次定向修订”的闭环；
- OpenAI 兼容模型只负责候选构造和解释，硬约束由 `assess_itinerary` 负责；
- NDJSON 流式展示执行过程，并持久化会话、证据、投票和最终方案；
- 成员投票确认胜出方向后，系统自动应用确认的约束变更并再次生成、补证和严格复检。

北京三人案例只是固定回归测试集，用来验证 Agent 在复杂冲突下的表现，不是产品逻辑本身。

## 7. 首条评测案例

案例 `beijing-friends-001` 描述三位朋友的北京 2 天 1 夜行程：

- 小林希望高密度参观故宫、景山、天坛和什刹海，可早起、可长距离步行；
- 阿哲预算只有 800 元，每日最多步行 4 公里，10:00 后出发且需要长午休；
- 小雨希望历史、自然和夜景，拒绝跨区折返、长时间乘车和过晚结束。

该案例覆盖六类冲突：行程密度、出发时间、步行能力、预算、必去地点与夜间结束时间。

正式通过必须满足：

- 三个候选方案全部不违反硬约束；
- 地点与路线证据可追溯；
- 必去地点被共同安排，或通过已确认支线满足；
- 三位成员均有明确收益与妥协；
- 最低成员满意度不低于 60；
- 成员能够从三个方案中选出至少一个可接受方案。

## 8. 首轮基线与问题发现

2026-09-04 使用固定案例 `beijing-friends-001` 进行了首轮正式基线测试：

| 指标 | 结果 |
|---|---:|
| 最终状态 | `blocked` |
| Agent 轮次 | 16 |
| 工具调用 | 25 次 |
| 工具错误 | 1 次 |
| 候选方案 | 0/3 |
| 自动评测总分 | 3.8/100 |
| 结论 | `NOT_QUALIFIED` |

Agent 成功调用了地点搜索和路线规划，但在 16 轮内反复收集信息，没有进入 `assess_itinerary` 和最终候选生成阶段；其中一次路线请求因缺少经纬度失败。各轮上报 Token 合计 508,373，暴露出明显的成本与延迟风险。

这次失败说明：复杂多人约束不能仅依靠更长 Prompt 和开放式 ReAct 循环解决。下一版需要改成有明确退出条件的分阶段编排：先结构化冲突，再执行有预算的地点检索与路线查询，然后一次生成三个候选，最后由确定性校验器逐个验收。

此外仍需解决：

1. 步行、饮食、必去与支线确认缺少确定性验证；
2. 模型最终输出不一定与最后一次通过校验的方案完全一致；
3. 当前输出协议仍以单方案为主；
4. 单一 JSON 文件存储不适合并发和长期运行。

这些问题不会被包装成“已解决”，而会作为后续迭代的可验证目标。

### 第一轮工程迭代结果

将开放式 ReAct 改为“有限地点检索 → 一次候选生成 → 有界路线取证 → 三方案逐个校验 → 最多一次定向修订”后，同一案例取得以下变化：

- 自动评测总分最高从 `3.8` 提升到 `92.0`；
- 候选方案从 `0/3` 提升到 `3/3`；
- 模型轮次从 `16` 降到 `2`；
- 一次协商版本运行 Token 为 `19,677`，相对初始 `508,373` 下降约 96.1%；
- 证据与共识得分最高均达到 `100`；
- 一次协商版本完成时间约 `58.2 秒`。

进一步验证后发现，原始硬约束无法全部同时满足，因此产品不再生成三份近似行程，而是生成三种明确协商方向：

1. 全员确认分组支线；
2. 小林确认降低故宫、景山的必去等级；
3. 阿哲确认将步行上限从 4 公里放宽到 6 公里。

协商版本严格评测为 `84.9`，但“协商方向就绪”为通过。严格分数下降源于主动、透明地列出待放宽条件，而不是系统质量回退。成员可选择 1～2 个方向投票，只有该方向涉及的成员完成确认后，系统才允许进入下一轮重规划。

## 9. 评测方案

项目采用四层评测：

- 硬约束：缺失证据也视为未通过；
- 事实证据：检查本次工具调用、地点与路线引用；
- 共识质量：检查冲突覆盖、候选差异、成员取舍与公平底线；
- 系统可靠性：统计完成率、工具成功率、重规划、耗时和 Token。

每次 Prompt、模型或工具变更后，对固定案例运行至少三次，保留修改前后报告，避免只展示一次“运气好的结果”。

## 10. 下一阶段计划

### P0：建立可信基线

- 扩充确定性校验器；
- 验证最终版本与通过校验版本一致；
- 输出三个候选方案；
- 增加地图证据追溯；
- 使用固定案例完成三次基线测试。

### P1：完成多人共识闭环

- 成员邀请与混合填写；
- 方案平铺对比；
- 单选/双选认可投票；
- 平票公平决策；
- 分组支线确认；
- 锁定节点后的局部重规划。

### P2：真实用户验证

- 访谈 5～8 位有多人旅行组织经验的用户；
- 进行至少 5 组可用性测试；
- 记录填写完成率、方案可接受率、投票分歧和修改次数；
- 根据真实反馈调整字段、流程和公平规则。

## 11. 个人贡献表达模板

> 我没有把项目停留在“调用大模型生成攻略”。我先将目标用户聚焦到 3～6 位朋友结伴游，把核心问题定义为多人偏好冲突。随后设计了硬约束一票否决、认可投票和最低满意度优先的混合公平机制，并用真实地图工具和确定性校验降低幻觉。为了避免只展示单次成功案例，我建立了标准测试案例和自动评测框架，用硬约束、证据、共识质量和系统稳定性四层指标持续评估迭代效果。

## 12. 待补充的真实证据

以下内容必须来自真实研究，不能由 AI 虚构：

- 用户访谈原始记录与洞察；
- 可用性测试观察；
- 成员真实投票与接受原因；
- 方案采纳率和修改次数；
- 迭代前后指标变化；
- 最终上线或试用数据。
