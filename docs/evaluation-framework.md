# “同行”多人旅行 Agent 评测体系

## 1. 评测目标

评测不只回答“模型有没有生成行程”，而要回答四个产品问题：

1. **底线是否守住**：预算、步行、时间、饮食、必去与禁去条件是否满足。
2. **事实是否可信**：地点与路线是否来自本次真实工具调用，引用能否追溯。
3. **共识是否形成**：冲突是否被识别，三个候选方案是否可比较，少数成员是否被忽略。
4. **系统是否稳定**：能否在限定轮次内完成，是否频繁报错、重试或输出无效 JSON。

## 2. 评测分层

### 2.1 硬约束层

硬约束采用一票否决。任何候选方案只要出现以下情况，就不能标记为“可投票方案”：

- 超过任一参与成员预算上限；
- 共同活动早于成员最早出发时间，或晚于最晚结束时间；
- 第二天未在截止时间前返回指定地点；
- 超过成员步行上限；
- 未满足必去要求，且没有经确认的个人/分组支线；
- 命中成员明确禁去、饮食过敏或安全限制；
- 交通、用餐、节点数量等明确数值规则被违反；
- 缺少关键字段，导致约束无法验证。

缺少证据时记为 `UNKNOWN`，不得当作通过。

### 2.2 事实证据层

自动检查：

- 最终 `evidence[].request_id` 是否存在于本次成功工具结果；
- 行程地点 ID 是否来自本次 `search_places`；
- 相邻节点路线引用是否来自本次 `get_route`；
- 路线起终点是否与相邻节点一致；
- 最终方案是否在输出前调用过 `assess_itinerary`；
- 最终提交版本是否与通过校验的版本一致。

### 2.3 共识质量层

自动指标：

- 候选方案数是否为 3；
- 是否至少包含一个均衡方案和两个冲突驱动方案；
- 预期冲突识别覆盖率；
- 成员取舍说明覆盖率；
- 各成员软偏好满意度；
- 最低成员满意度（公平底线）；
- 平均满意度与满意度差距。

人工评审：

- 三个方案是否真的有差异，而不是换标题；
- 取舍说明是否准确、不甩锅；
- 协商选项是否可执行；
- 成员是否愿意投票选择至少一个方案。

### 2.4 系统可靠性层

记录：

- 完成率；
- 工具调用成功率；
- 最终 JSON 解析成功率；
- 自动重规划次数；
- 总轮次与耗时；
- Token 使用量；
- 单轮工具调用是否超过 3 次；
- 阻塞、外部 API 配额与超时错误。

## 3. 核心指标

| 指标 | 计算方式 | 首版目标 |
|---|---|---:|
| 硬约束可验证通过率 | `PASS / 全部硬约束`，`UNKNOWN` 计未通过 | 100% |
| 最终完整通过率 | 全部硬约束通过且证据覆盖达标的案例占比 | ≥80% |
| 地点证据覆盖率 | 有真实地点搜索证据的行程地点 / 应验证地点 | ≥95% |
| 路线证据覆盖率 | 有真实路线证据的相邻节点 / 应验证路线 | ≥95% |
| 引用有效率 | 能在本次工具结果中找到的引用 / 全部引用 | 100% |
| 冲突识别覆盖率 | 被识别的预期冲突 / 预期冲突 | ≥80% |
| 成员取舍覆盖率 | 有 gains/concessions 的成员 / 全部成员 | 100% |
| 公平底线 | 所有成员满意度中的最低值 | ≥60 |
| 满意度差距 | 最高满意度 - 最低满意度 | ≤25 |
| 三方案合规率 | 满足硬约束的候选方案 / 3 | 100% |
| JSON 成功率 | 首次或修复后得到合法结构化结果的运行占比 | ≥95% |
| 工具成功率 | 成功工具调用 / 全部工具调用 | ≥95% |

## 4. 满意度计算

首版采用三级软偏好：

- `很想要`：每项权重 3；
- `可以有`：每项权重 1；
- `不感兴趣`：不加分，若方案明显强化该内容可在人工评审中扣分。

成员满意度：

`已覆盖偏好权重 / 全部正向偏好权重 × 100`

团队指标：

- `fairness_floor`：最低成员满意度；
- `average_satisfaction`：平均满意度；
- `satisfaction_gap`：最高与最低满意度之差。

选方案时先保证硬约束，再依据认可投票；平票依次比较公平底线、硬约束满足率、平均满意度，最后由组织者决定。

## 5. 评测案例规范

案例文件放在 `evaluation/cases/`，必须包含：

- 共同旅行边界；
- 每位成员的预算、步行、起止时间；
- 必去、禁去与饮食限制；
- 三级软偏好；
- 可量化规则；
- 预期冲突；
- 候选方案与投票规则；
- 需要真人判断的问题。

首条案例为 `beijing-friends-001.json`。

## 6. 自动评测使用方式

1. 配置 `.env` 并启动服务。
2. 执行 `npm run test:agent`，生成带案例标识的 `data/test-run.ndjson`。
3. 执行 `npm run eval`，生成 `data/evaluation-report.json`。
4. 查看报告中的：
   - `qualified`；
   - `candidate_reports[].hard_constraints`；
   - `evidence`；
   - `consensus`；
   - `reliability`；
   - `manual_review`。

也可评测指定历史会话：

```powershell
npm run eval -- --session <session_id>
```

历史会话若不是用同一案例运行，会被标记为案例不匹配，不能作为该案例的正式成绩。

## 7. 实验与迭代方法

每次修改 Prompt、模型、工具或校验器后：

1. 固定案例和模型参数运行至少 3 次；
2. 记录通过率、平均耗时、Token 与重规划次数；
3. 对失败原因归类：检索失败、规划失败、结构失败、约束失败、证据失败；
4. 只针对高频失败做产品或工程修改；
5. 保留修改前后报告，形成作品集中的迭代证据。

## 8. 首轮正式基线

2026-09-04 使用 `beijing-friends-001` 完成首轮正式运行，会话 ID 为 `10f8f7e1-086f-427b-8028-07d55b07a719`。结果保存在 `data/evaluation-report.json`。

| 项目 | 结果 |
|---|---:|
| 案例匹配 | 是 |
| 最终状态 | `blocked` |
| Agent 轮次 | 16 |
| 工具调用 | 25 |
| 工具错误 | 1 |
| 已调用工具 | `search_places`、`get_route` |
| 缺失工具 | `assess_itinerary` |
| 候选方案 | 0/3 |
| 报告总分 | 3.8/100 |
| 自动评测结论 | `NOT_QUALIFIED` |

失败并非来自地图完全不可用：Agent 已成功获得大量地点和路线证据。主要问题是开放式循环缺少明确阶段和工具预算，模型反复检索，在最大 16 轮内仍未进入候选生成与最终校验。一次路线调用还因缺少经纬度失败。各轮上报 Token 合计为 508,373，说明当前策略同时存在明显的延迟与成本风险。

这份低分报告是有效的产品证据：它证明复杂多人约束不能仅靠扩大 Prompt 和轮次解决。

完成分阶段编排后，同一案例经历两步迭代：

| 项目 | 开放式循环 | 分阶段可行性方案 | 三方向协商方案 |
|---|---:|---:|---:|
| 总分 | 3.8 | 92.0 | 84.9 |
| 最终状态 | `blocked` | 返回 3 个候选 | 返回 3 个协商方向 |
| 模型调用轮次 | 16 | 2 | 2 |
| Token 合计 | 508,373 | 20,810 | 19,677 |
| 硬约束得分 | 0 | 80 | 64 |
| 证据得分 | 0 | 100 | 97 |
| 共识得分 | 0 | 100 | 100 |
| 稳定性得分 | 25 | 100 | 100 |
| 协商方向就绪 | 否 | 否 | 是 |

严格总分在协商版本下降，是因为三个候选分别显式放宽“全员同行”“部分必去等级”“步行上限”，评测器仍按原始硬约束扣分。这不是隐藏违规：页面会明确展示放宽项和必须确认的成员，并允许成员对 1～2 个方向投票。只有所需成员完成确认后，胜出方向才进入下一轮收敛规划。
